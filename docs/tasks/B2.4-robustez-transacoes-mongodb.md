## 4. Comportamento anterior vs corrigido

### 4.1 Lifecycle — Unknown

| | Antes | Depois |
|---|-------|--------|
| `UnknownTransactionCommitResult` | Tratado como transitório → **nova sessão + callback completo** | **Só** re-`commitTransaction` na **mesma sessão** (até 8×) |
| Callback após Unknown no commit | Reexecutado | **Não** reexecutado |
| Limite commit ambíguo | N/A | `LIFECYCLE_COMMIT_MAX_ATTEMPTS = 8` |

### 4.2 Lifecycle — Transitório / 112

| | Antes | Depois |
|---|-------|--------|
| Callback ou commit (não-Unknown) | Retry integral até 4× | Igual, com **backoff** 5–50 ms (full jitter) entre tentativas |
| `AppError` | Sem retry (não era transitório) | Mantido |

### 4.3 `referenceNow`

| | Antes | Depois |
|---|-------|--------|
| Instante | `new Date()` **antes** de `withCompanyLifecycleTransaction` | `new Date()` **no início de cada** execução do callback |
| Retries integrais | Mesmo instante | Novo instante por tentativa |

## 5. Decisão `UnknownTransactionCommitResult`

Alinhado a [`withBookingTransaction`](../../server/src/modules/appointments/services/appointment-booking-transaction.ts): resultado ambíguo de commit **não** implica reexecução do trabalho de negócio; apenas clarifica o commit na sessão corrente.

---

## 6. `TransientTransactionError` e código 112

- **Lifecycle e booking:** retry integral com nova sessão, abort, backoff (lifecycle e booking), `AppError` excluído.
- **Unknown:** removido da classificação de retry integral no lifecycle.

---

## 7. Backoff e política de retry (Req E — Critério B)

Constantes partilhadas: `BACKOFF_BASE_MS = 5`, `BACKOFF_MAX_MS = 50`, full jitter (`computeLifecycleTransactionBackoffMs` / equivalente booking).

### 7.1 Retry integral (nova sessão)

Aplica-se a erros **transitórios** na callback ou no commit (**excepto** `UnknownTransactionCommitResult`): `TransientTransactionError`, código MongoDB **112** (Write Conflict), e falhas de commit não classificadas como Unknown.

- Nova `ClientSession`, `abortTransaction` na tentativa falhada, **reexecução da callback**.
- Backoff com jitter **entre** tentativas integrais.
- Limites: `COMPANY_LIFECYCLE_MAX_ATTEMPTS = 4` (lifecycle); `BOOKING_TRANSACTION_MAX_ATTEMPTS = 8` (booking).
- `AppError` **não** é reententado.
- Ver também §6.

### 7.2 `UnknownTransactionCommitResult` no commit (paridade booking)

Quando o commit devolve resultado ambíguo (label `UnknownTransactionCommitResult`):

| Aspeto | Comportamento |
|--------|----------------|
| O que é reententado | **Apenas** `commitTransaction` |
| Sessão e transação | **Mesma** `ClientSession`; transação mantida aberta (sem novo `startTransaction` entre retries Unknown) |
| Callback de negócio | **Não** reexecuta |
| Limite | Até **8** tentativas de commit (`LIFECYCLE_COMMIT_MAX_ATTEMPTS` / `BOOKING_TRANSACTION_MAX_ATTEMPTS`) |
| Backoff | **Permitido** — jitter entre tentativas de commit Unknown (`commitWithUnknownResultRetries`), alinhado a `withBookingTransaction` |
| Retry integral | **Não** — após esgotar commits Unknown o erro propaga; Unknown não entra em `isRetryableLifecycleTransactionError` |
| Logging | Booking regista `logCommitRetry`; lifecycle regista apenas esgotamento (`logExhaustedRetries`) |

Ver §4.1 e §5.

### Inventário lifecycle (comportamento)

1. Sucesso (start/commit/end, sem abort)  
2. Unknown → 2º commit OK (1× callback)  
3. Unknown esgotado  
4. Transient no callback  
5. 112 no callback  
6. Transient no commit → retry integral  
7. AppError sem retry  
8. Erro genérico  
9. abort falha preserva erro  
10. endSession falha log + erro primário  
11. Esgotamento retry integral (4×)

### Booking (acréscimos)

- Transient no commit  
- Esgotamento retry integral (8×)  
- abort + endSession antes da 2ª sessão  
- Happy path: `startTransaction`, `endSession`, sem `abort`

## 11. Limitações e riscos residuais

- Retry integral após commit transitório **reexecuta** o callback (incl. `softDelete` na 1ª tentativa abortada) — esperado em transações Mongo; teste `referenceNow` usa `softDelete >= 1`.
- Lifecycle: 4 tentativas integrais vs 8 commits Unknown — simetria intencional com booking no commit, não no loop externo.
- Contenção mongo + backoff pode alongar testes de integração (manter `--maxWorkers=1` quando necessário).
