## 6. Resultado da auditoria — `withBookingTransaction`

**Implementação (resumo):**

- `BOOKING_TRANSACTION_MAX_ATTEMPTS = 8`.
- Separação clara: Unknown → só `commitWithUnknownResultRetries`; Transient/112 → novo loop com nova sessão.
- `AppError` explicitamente excluído de retry.
- Backoff full jitter 5–50 ms.
- `endSession` sempre no `finally`; falhas logadas.

**Testes:** Ficheiro dedicado com boa cobertura dos caminhos **documentados na equipa**. Lacunas principais:

1. Transitório/`112` no **commit** (não Unknown) — sem teste que force `commitTransaction` a falhar com `TransientTransactionError`.
2. Esgotamento de **8 tentativas** de transação integral (só esgotamento de commit Unknown).
3. Happy path não asserta `endSession` / `startTransaction`.
4. Integração real (mongo) não substitui testes de falha simulada.

**Conclusão:** Mecanismo **razoavelmente protegido por testes unitários**; não considerar 100% coberto sem os gaps acima.

## 7. Resultado da auditoria — `withCompanyLifecycleTransaction`

**Implementação (resumo):**

- `MAX_ATTEMPTS = 4`.
- Fluxo linear: `startTransaction` → `operation` → `commitTransaction`.
- Qualquer erro em `catch`: `abort` (falhas ignoradas) → se `isTransientTransactionError` e tentativas restantes → `continue` (nova sessão, **callback de novo**).
- `isTransientTransactionError` inclui **112**, **TransientTransactionError** e **UnknownTransactionCommitResult** (L15–17).
- Sem backoff.
- Sem distinção AppError (mas `AppError` típico não tem labels → não retry).
- `lastError` após loop pode ser lançado (L48); caminho raro se loop esvazia sem throw.

**Testes:** **Zero** cobertura directa.

**Conclusão:** Comportamento inferido **apenas por leitura de código**. Risco elevado de regressão no delete B2 sem suite espelhando `appointment-booking-transaction.test.ts`.

## 8. Análise `UnknownTransactionCommitResult`

### Booking (comportamento desejado na revisão B2)

```text
operation() → commitWithUnknownResultRetries:
  em Unknown: re-commit na MESMA sessão (até 8×)
  em outro erro no commit: abort + possível retry INTEGRAL
```

**Evidência:** teste `retries commit only on UnknownTransactionCommitResult without re-running the callback` — **COBERTO**.

### Lifecycle (desvio identificado)

Em `withCompanyLifecycleTransaction`, `commitTransaction()` está no mesmo `try` que `operation(session)`. Se `commitTransaction` falhar com `UnknownTransactionCommitResult`:

1. `catch` classifica como `isTransientTransactionError` (L17).
2. `abortTransaction`, `endSession` (`finally`).
3. Nova iteração: **novo** `startSession`, **nova** execução completa do callback.

**Consequência:** Duplo `touchBookingSerialization`, re-leituras `hasOpen`, possível duplicidade de efeitos se o callback não for estritamente idempotente.

**Comportamento incorreto comprovado por teste?** **Não** — nenhum teste lifecycle. **Confirmado por análise estática** do código L29–39 + L15–17.

### Teste hipotético (B2.4, não implementado)

Mock semelhante ao booking:

1. `operation` resolve na 1ª chamada.
2. `commitTransaction` rejeita 1× com `{ errorLabels: ['UnknownTransactionCommitResult'] }`, depois resolve.
3. **Esperado (design booking):** `operation` 1×, `commit` 2×, `startSession` 1×.
4. **Esperado (lifecycle actual):** após 1ª falha de commit, `operation` **2×**, `startSession` **2×** (comportamento actual presumível).

## 10. Análise do `referenceNow` (`CompanyService.delete`)

Trecho relevante ([`CompanyService.ts`](../../server/src/modules/companies/services/CompanyService.ts) L254–338):

```ts
const referenceNow = new Date();

await withCompanyLifecycleTransaction(async (session) => {
  // hasOpenAppointmentsForCompany(id, referenceNow, { session }) — várias vezes
  // hasOpenAppointmentsForCompany(id, referenceNow) — committed, sem session
});
```

**Observações:**

1. `referenceNow` é fixado **antes** de `withCompanyLifecycleTransaction`, **fora** do loop de retry interno do helper.
2. Se o lifecycle fizer retry integral (transitório/Unknown/112 no commit), o **mesmo** `referenceNow` é reutilizado em todas as tentativas do callback.
3. Gate “aberto” = `endAt > referenceNow` (SCHEDULED/CONFIRMED).

**Risco analisado (409 indevido após fim natural do agendamento):**

- Cenário: delete inicia com agendamento ainda “aberto” relativamente a `referenceNow`; durante retries (tempo real avança), o agendamento **termina** (`endAt` passou no relógio mural).
- Com `referenceNow` congelado, `hasOpen` pode continuar **true** nas tentativas seguintes → **409** ou bloqueio prolongado até esgotar retries, mesmo que o agendamento já não esteja em curso no presente real.

**Risco inverso** (delete passar com agendamento que ficou aberto durante retry): menos provável com instante congelado no passado; possível se leituras committed divergirem do snapshot — já mitigado em parte pelas leituras `hasOpenCommitted`.

**Recomendação conceptual (sem implementação):**

- Recalcular `referenceNow = new Date()` no **início de cada tentativa** (primeira linha do callback ou no wrapper antes de `operation`), **ou** imediatamente antes de cada par `hasOpen*`.
- Documentar se a intenção é “gate no instante do pedido” vs “gate no instante da tentativa de commit”.

**Testes:** **NÃO COBERTO** (nenhum teste de relógio + retry lifecycle).
